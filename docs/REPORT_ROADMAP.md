# 附件六测试路线图与证据清单

本文件依据用户提供的《附件六：信息系统股票期权接入测试报告模板》和本次补充的八项检查要求编写。用于分阶段开发和收集证据，**不是已经通过的测试报告**。

v0.5.0 除连接、交易端认证及登录、只读查询和行情端登录外，提供受显式确认保护的单次 GFD 限价委托，报单数量固定为 1；默认排队后撤单，也可选择等待成交、超时后最多撤单一次。每日和每秒最大报单量采用同一入口联合检查、持久计数和本地拦截，并提供设置及两种触发自测弹窗。新增 `rate-live` 在一次登录内最多发送 N 笔、每笔 1 张，验证每秒限额并清理未结束委托。用户 2026-09-15 的 Windows 评测日志记录过 SSE 委托被接受、排队后撤单成功；v0.5.0 的原生 Windows 构建、真实每秒测试、新弹窗和成交测试仍需现场执行，不能据此勾选两所基础功能均已实测、三项风控全部通过或穿透式监管通过。

## 1. 当前阶段要证明什么

| 编号 | 本阶段检查 | 成功依据 | 不能由此得出的结论 |
| --- | --- | --- | --- |
| C01 | 交易前置连接 | 收到交易 API 的 `OnFrontConnected` | 不能说明账户已登录或认证码有效 |
| C02 | 交易端客户端认证 | 对应 `ReqAuthenticate` 的认证响应明确成功 | 不能说明交易账户已登录 |
| C03 | 交易账户登录 | 对应登录请求的 `OnRspUserLogin` 响应明确成功，并记录账户、登录时间、交易日等可用信息 | 不能说明已成交或监管终端信息已通过后台核验 |
| C04 | 交易端只读查询 | 查询请求得到对应正常响应，并收到最后一条响应；具体查询项目见运行说明 | 查询无数据不等于 API 不通；查询成功不等于具备下单权限 |
| C05 | 行情前置连接及登录 | 行情 API 收到连接回调，并收到对应成功登录响应 | 不能说明已订阅合约或已经收到实时行情 |
| C06 | 失败定位 | 区分连接、认证、登录、查询阶段；保存错误码、时间和超时位置 | 请求函数返回 `0` 仅表示提交被接受，不能替代异步业务成功响应 |

上述项目都需要在实际运行后记录“成功 / 失败 / 未执行”。交付代码、编译成功或离线验证不能代替账户登录测试，也不能填入虚构的成功截图。

## 3. 分阶段推进

### 阶段一：实体机连接和登录

1. 在用户实际用于测试的 Windows 实体机上准备匹配架构的评测版 API，管理员权限运行程序；使用券商给出的个股期权评测环境。
2. 分别运行交易端和行情端连接测试，定位连接、认证、登录、查询是否成功。
3. 保存实际软件版本、API 版本、测试日期、时区、时间段、交易日和原始结果日志。
4. 登录成功后当天及时告知券商，请其核验测试账号、APPID 及终端采集信息。根据用户说明，后台只能查询当天记录，不能留待次日再核验。
5. 报告登录截图需要包含账号信息；录像覆盖从启动程序到登录结果的过程，录制时避免把密码或授权码展示出来。

本阶段不以交易所成交、行情订阅或风控完成为验收条件。

### 阶段二：基础交易能力

1. 已增加明确可控的单次报单及撤单/成交目标：`--order-goal cancel` 默认在排队后撤单；`--order-goal fill --fill-wait 10` 等待完整成交，等待参数为 `1..300` 秒。下一步补充委托查询、成交与持仓展示，并按最终申报范围完善策略说明。
2. 确认账户在上交所、深交所的可用测试权限、合约及测试时段后，分别完成交易验证，保存交易所、合约、委托及成交证据。只查到两个交易所的合约不等于完成两个交易所的交易。
3. 按用户检查要求，登录和交易当天及时告知券商，提供准确时间段；由券商核验后台记录。不能把程序自行输出的“成功”当作券商后台已确认。
4. 根据最终软件实际功能完善基础功能截图及完整功能演示录屏。

成交目标只有完整成交才通过；等待超时后确认撤单意味着 `fill=NOT_FILLED cancel=PASS`，成交测试仍失败。不能从“撤单成功”推导“成交成功”。若日志显示 `residual_order=UNKNOWN`，必须在终端核对活动委托与成交。`basic` 最多发送 1 笔 1 张、最多撤单一次，不自动重试或追价。

### 阶段三：三项风控

两个数量阈值必须从正式报备表取得，不能随意填写演示值作为申报值。在本地 INI 的 `[risk]` 中分别设置 `daily_max_order_count` 与 `per_second_max_order_count`，均为 `1..999999999` 的正整数。两个数量限额已有实现与截图入口；异常价格检查仍待实现。基础实发、`rate-live` 计划/实发及设置/触发自测要求两个阈值，缺项时在索取凭据和联网前停止；普通连接与基础 dry-run 不要求阈值。

| 风控 | 必须确定的口径 | 报告证据 |
| --- | --- | --- |
| 每日最大报单量 | 按本机器、本项目目录内的 BrokerID/UserID 累计；每次 `ReqOrderInsert` 尝试计 1，SDK 返回失败和柜台拒单也计，撤单不计；跨进程及重启持续，交易日切换归零 | 设置截图清楚显示与报备表一致的阈值；`trigger` 离线触发截图显示阈值、注入计数和本地阻止动作 |
| 每秒最大报单量 | 同一作用域、相同尝试计数口径；最近 1000 毫秒滚动窗口，非自然秒清零；与每日判断共同放行或拦截，被拦截时两项额度均不增加；不限制撤单 | 设置截图显示正式阈值；`trigger-second` 离线截图显示窗口、注入计数和提示；真实检查日志提供 `peak_per_second` 等观察记录 |
| 价格异常 | 使用的价格边界、偏离参考价规则或其他实际申报规则；无有效参考行情时的行为 | 价格异常提示截图，展示输入、检查依据及处理结果；同时录屏 |

测试用例需覆盖阈值内、达到阈值、超出阈值、窗口到期、每日与每秒联合拦截、持久化和交易日切换，已执行范围以 `docs/VALIDATION.md` 为准。`run_risk_windows.bat settings` 同时显示两个阈值；`trigger` 和 `trigger-second` 通过临时注入“已计数=阈值”触发实际判断，不读写真实计数、不索取凭据、不连网、不发单，并明确标识离线自测及 `api_call=NOT_SENT`。不能把该注入计数或峰值写成真实报单吞吐量。

状态文件共享每日计数、近期系统运行时间戳与观察峰值，v0.3.0 旧文件升级时保留每日计数。交易日变化重置每日计数和峰值，但最近窗口时间戳继续参与每秒判断；Windows 命名互斥锁覆盖实际 SDK 提交，提交异常退出留下未完成标记时拒绝后续报单。该计数不会合并其他机器、其他软件或其他项目副本，正式报备前应核对作用域和滚动窗口口径。

正式截图必须来自与报备表一致的设置，不得修改截图数字。`basic` 一次只尝试一笔委托，连续手动启动通常无法达到每秒阈值。需要实际报单验证时使用 `run_rate_windows.bat`，参数和完整命令见 README，不用 PowerShell 并发循环，也不能清空每日状态解除限制。

真实每秒测试的用例边界为：`--max-orders N` 必须等于正式每秒限额，N 为 `1..10`；本交易日剩余报单额度至少为 N+1，开始时最近 1000 毫秒窗口为空。两项配置仍保持报备值，不满足前提时程序不发单。正式每秒阈值大于 10 时保留配置，当前入口不支持其真实峰值测试；不得降低阈值冒充正式验收。

不带实发开关的 `rate-live` 在读取凭据和联网前只输出计划。使用 `--send-order --confirm SEND_RATE_TEST_ORDERS` 才在一次登录内最多真实提交 N 笔，每笔 1 张。第 N+1 次只检查风控、绝不发送；预期在同一滚动窗口被每秒限额阻止。记录实际 SDK 调用数量、观察峰值、额外检查的 `api_call=NOT_SENT`，以及每笔接受、拒单、成交及撤单结果。窗口超时、预算耗尽、SDK 错误、柜台拒单或其他不符合预期的情况使本次失败，不自动重试或追价。

实发可能成交最多 N 张。程序在显示触发弹窗之前，对未结束委托分别最多撤单一次并按共同截止时间等待清理结果；终态不明时必须在交易终端人工核查，成交不自动反向平仓。不能只截触发窗口、忽略失败或残留委托。该入口的 Windows 构建、柜台速率和弹窗须现场验证，离线回归通过不能替代实际峰值测试。

### 阶段四：证据和提交包

1. 录制程序功能演示，覆盖报告中每个需要截图的功能点，包括登录、基础功能及风控；价格异常需要对应录像。
2. 编写图文使用手册，至少覆盖报告测试点：环境准备、管理员启动、登录、行情与交易功能、风控设置、触发提示、日志和故障处理。
3. 固定交付版本，记录软件版本与 API 版本，整理实际执行目录，打出程序压缩包或安装包并备份。
4. 对该最终文件计算 MD5，保存文件名、大小、MD5 和计算时间；可以同时保留 SHA-256。任何重打包都会产生新的待核对文件，必须重新计算。
5. 对同一最终包执行病毒检测，保存检测工具名称、检测日期和结果。MD5 只能帮助确认文件一致性，不能证明软件无病毒。
6. 将真实截图、录像、手册、最终包及校验记录逐项对应到附件六，再办理盖章或签字。

## 4. 终端采集与原生 API 的边界

本项目使用用户提供的个股期权原生 SDK。不要仅凭 `OnRspUserLogin` 成功就写“穿透式监管已通过”，也不要因为能列出本机网卡信息就认为券商后台已经收到完整终端信息。

附件 SDK 的登录结构 `CThostFtdcReqUserLoginField` 存在 `MacAddress`、`ClientIPAddress`、`ClientIPPort` 等字段；这些字段的存在并不证明当前运行中实际完成了什么采集。报告需要本机内网 IP 和 MAC 时，应核对真实测试终端及实际使用的网卡，不能随意选择 VPN、虚拟网卡或容器网卡信息填报，也不能填写预设或伪造设备信息。

附件交易 API 头文件将 `RegisterUserSystemInfo` 注释为“中继服务器多连接模式”，将 `SubmitUserSystemInfo` 注释为“中继服务器操作员登录模式”。本次业务信息为直连接入，因此不能为了出现一个“上报成功”的日志就照搬中继接口调用；也不能伪造采集数据填充接口。

原生 API 是否已经按该版本要求完整采集，以及后台看到的终端标识是否正确，需要结合供应商对该评测包的说明和券商当天后台核验确认。实体机、管理员权限、正确评测 API 与正确环境是本次检查要求的一部分。开发环境中的编译或离线测试不能替代这项验证。

直连报告中的 `RELAYAPPID` 与中继代理公网 IP 可按模板注明“不适用（直连）”；若以后接入方式改成中继，必须重新核对接口流程与报告信息。

## 5. 建议保留的证据记录

每次正式测试建立独立记录，内容至少包括：

- 软件名称、版本、API 版本、最终可执行文件或程序包识别信息。
- 测试日期与时区、开始结束时间、交易日、测试账号和 APPID。
- 实际环境、终端内网 IP、MAC、实体机与管理员运行情况。
- 本次执行的测试编号、步骤、预期结果、实际结果和证据文件名。
- 与报备表一致的正式阈值；来源报备表的版本或日期。
- 当天通知券商的时间以及后台核验结论；未核验时写“待核验”。

原始日志、截图和录像以实际执行为准。测试失败也应保留真实结果，修复后另存新的测试记录；不要覆盖失败记录或将未执行的项目写成通过。
